### Benchmark build

**You own what the number means. Build a harness the user trusts, then hand it over.** For an app metric that has no rerunnable measurement yet (latency, throughput, memory, startup time, bundle size, query count). Perf issue and Hillclimb start from its baseline. One flow per harness. Six slow flows are six harnesses, so build the one asked about and stop.

1. Pin the flow and its entry point. Name the one user-facing flow and the metric a user would feel (p50 and p99 of the request, time to first paint, rows per second). Run the **how** skill to find the endpoint, command, or function a real request goes through, and measure through it. A script that reimplements the flow measures the script.
2. Reuse what exists. Search for existing benchmarks, load-test scripts, fixtures, seed data, and recorded traces. Wrap an existing harness with a thin adapter instead of replacing it. Say which pieces you reuse and which you add before writing anything.
3. Choose the workloads. Source them in this order, using the first that is available and safe to keep. Production traces or logs (request mix, payload sizes, data volumes) come first, then bug reports and "this is slow" tickets, then cases the user names, then cases synthesized from the code and anchored on a few real ones. Before copying production data, check its retention policy and whether it holds personal data. If either blocks keeping it, store identifiers or a scrubbed shape instead. Cover the dimensions that move the metric (data size, history, state, concurrency, cold versus warm) with a realistic case, a heavy case, and the case behind any complaint. Tag each workload with the dimension it stresses.
4. Make the environment reproducible. Seed databases and file state from fixtures. Pin versions and config to what production runs (question 2 of the **benchmark-checklist** skill). Stub anything with real side effects (email, payments, writes to shared systems) at the boundary, and keep the code under test real. Record a fingerprint with every run: commit, lockfile hash, runtime version, machine, and config.
5. Get the plan approved before the first full run. Show the user the workload list (id, dimension, size, source), the metric and how it is computed, the secondary metrics recorded beside it, and what is stubbed. Wait for a clear yes. A "mostly, but" means fix it and show it again. This and the pilot check in step 7 are the only stops for the user.
6. Build the runner as a lever (the **build-the-lever** principle skill), in the repo's own language and test tooling, with no new framework. Delegate it to a subagent using your configured perf-issue model and review the diff. The runner must:
   - Warm up, then sample each workload enough to report the median and range, plus percentiles for latency.
   - Check that each output is correct, not just present, and count errors and the work done (questions 4 and 7 of the **benchmark-checklist** skill).
   - Enforce a time limit per case and record a timeout as a timeout, never as a number.
   - Count retries instead of hiding them.
   - Write each result as it finishes, keyed by workload and sample, so a crash keeps finished work and a rerun resumes.
   - Record secondary metrics (memory, CPU, allocations, query count, payload size) as separate columns, not folded into the headline.
   - Print one summary line per workload with the metric, median, range, sample count, and error count.
7. Pilot and vet. Run two or three workloads and vet the run with the **benchmark-checklist** skill. Recompute the summary from the raw per-sample rows yourself. A zero, a constant across every workload, or a result past a hardware limit is a harness bug until proven otherwise. Confirm the harness separates the heavy case from the light one. If it can't, change the workload or the metric. Show the user the pilot numbers and ask whether they match what production shows.
8. Take the baseline. Run every workload at the agreed sample count on a quiet machine. Record the noise floor (run-to-run spread) per workload, the limiter (question 1 of the **benchmark-checklist** skill), and the commit. Report absolute numbers first ("p50 41 ms, 120 MB RSS") and relative changes after.
9. Make it durable. Commit the runner, workload definitions, fixtures, and a short README with the one command that reruns it and the baseline it produced. Keep raw run output out of the tree (gitignored). Then run **Opening a PR**.

**Reply:** the flow and metric, the one rerun command, each workload with its baseline (median, range, sample count) and noise floor, the limiter, what is stubbed, and the next playbook (Perf issue or Hillclimb) if the user wants the number moved.

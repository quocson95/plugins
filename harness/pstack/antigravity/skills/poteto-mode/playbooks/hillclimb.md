### Hillclimb

**You own the metric and the experiment's integrity. Supervise and review. Delegate the attempts.** For sustained, iterative improvement of one measurable thing against a target. A one-off fix is Bug fix or Perf issue. This is the loop.

Core discipline: one change, one measurement, keep or revert. Never stack untested changes, and never claim a win from code inspection (the **prove-it-works** principle skill).

1. Ground the workload and architecture before choosing the metric. Run the **how** skill over the target, name the realistic workload dimensions that can move the result (data size, history, state, concurrency), and select a case that reproduces the user's complaint. If no case reproduces it, fix the repro instead of hillclimbing. Then fix one metric, the direction that counts as better, and a checkable stop predicate that pairs a target with a floor on attempts so a lucky early win can't end the run (the example "at least 50% better than baseline and at least 10 iterations" is this shape). Name the guardrails, the secondary metrics that must hold within noise (memory, allocations, bundle or binary size, p99 when climbing p50), and the off-limits paths no attempt may touch, at minimum the harness and the regression gate. Use the user's numbers when given, otherwise agree them.
2. Build the measurement harness, prove its sensitivity, then freeze it. When the metric has no rerunnable harness yet, run the Benchmark build playbook (`playbooks/benchmark-build.md`) first and start from its harness (the **build-the-lever** principle skill). Run contrasting realistic workloads and confirm the target case reproduces the symptom while easier cases separate as expected. If the harness cannot distinguish them, revise the workload or metric. Keep those contrasting workloads: they are the hold-out check in step 8. Vet the harness with the **benchmark-checklist** skill before you freeze it, and make it print its error count, a count of the work done, and the guardrail metrics. Once frozen, one repeatable command emits the metric, sampled enough to clear the noise (median of N, not a single run). Record the baseline metric, a green run of the regression gate (the tests that must keep passing), and the commit that froze the harness before any change. From the baseline runs, record three numbers: the noise floor (run-to-run spread), the headroom (what the limiter allows, per the **explain-the-number** principle skill), and the smallest win worth keeping. If the noise floor is larger than that smallest win, or than the headroom, tighten the harness (more samples, a quieter machine, a finer metric) before the first attempt. The stop target and the keep threshold must both sit above the noise floor.
3. Open the decision log via the **show-me-your-work** skill. A `decision.tsv`, with a header recording the metric, predicate, noise floor, guardrails, off-limits paths, and harness commit, then one row per attempt: id, hypothesis, change, before, after, delta, guardrails, tests, verdict (kept or reverted), patch, note. Save every attempt's diff to `attempts/<id>.patch` beside the log, kept or reverted, so a reverted near-miss can come back. Read the log before each attempt. Keep it out of the tree (gitignored).
4. Ground each hypothesis in the architecture model from step 1, so it names a specific mechanism ("defer X off the boot path because it blocks first paint"), not "try memoizing something". For a perf metric, order hypotheses by the performance mantras in step 2 of the Perf issue playbook (`playbooks/perf-issue.md`). Borrow only their order, not that step's stop rule.
5. Loop, one hypothesis per iteration:
   - Hand the change to a subagent using your configured hillclimb model (default `grok-4.7-xhigh-fast`) with a tight scope that lists the off-limits paths. Pick each subagent's reasoning level and fast or standard speed for the job, per the Subagents section. Supervise and review the diff rather than typing it (the **guard-the-context-window** principle skill). Reject any diff that touches the harness or the regression gate, whatever the number says. When several independent hypotheses are live, fan the implementations to parallel subagents, each in its own worktree (the **separate-before-serializing-shared-state** principle skill), but measure them one at a time on a quiet machine. Concurrent benchmarks share the CPU, memory, and disk, and pollute each other's numbers.
   - Measure before and after with the frozen harness, and run the regression gate.
   - Accept only when the delta clears the noise floor, every guardrail holds within noise, and the gate stays green. Otherwise revert the change in full. A tweak that "might help" is not kept.
   - When two parallel attempts both win against the same base, keep the first, rebase the second onto it, and measure it again before keeping it. Two wins measured apart are an untested stack.
   - One commit per accepted fix, staging only the files you changed (`git add <files>`, never `-A`). Log the row and save the patch either way, kept or reverted.
   Each iteration ends in a check before the next begins (the **sequence-verifiable-units** principle skill). If the run is unattended, borrow only the wake mechanism from the Autonomous run playbook (`playbooks/autonomous-run.md`), not its stop rule.
6. Push past the first plateau. Each accepted win moves the limiter, so on a stall (several rejects in a row) profile again and name the current limiter before the next hypothesis (question 1 of the **benchmark-checklist** skill). If the limiter now sits in an off-limits path, the harness, or the load generator, or the deltas sit inside the noise floor, surface it instead of grinding. Otherwise pivot category, combine near-misses from their saved patches, re-read the source, or try something more radical before concluding the hill is climbed. Correctness and simplicity outrank the number. Revert a win that breaks behavior, and keep a simplification that holds the number (the **laziness-protocol** principle skill).
7. Stop when the predicate is met, or when the remaining ideas are marginal and not worth their cost. Don't relax the predicate to meet it, and don't quit while cheap untried hypotheses remain. If you are stuck, surface it instead of spinning.
8. Confirm the result directly, not as a sum of per-attempt deltas. Run the base commit and the final commit interleaved (A, B, A, B) with the frozen harness on the target case and on the contrasting workloads from step 2. A win only on the target case that regresses the others was tuned to that case: say so, and revert the commits that cause the regression. If the target delta is within noise, report that plainly instead of claiming a win.
9. Run **Opening a PR** with the accepted commits stacked in the order they landed.

**Reply:** the metric and target, baseline to final from the step 8 run with the percent delta, run count, and range, the contrasting workloads and guardrails from that run, iterations run (kept vs reverted), each accepted fix on one line, the `decision.tsv` path, and the best idea you would try next if pushed further.
